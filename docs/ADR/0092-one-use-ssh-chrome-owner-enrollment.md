# ADR 0092: Single-use Chrome owner enrollment without opening the owner volume to HTTP

**Status:** protected host-integration **PR candidate** for [issue #225](https://github.com/mbalbo2023/boca-socios-assistant/issues/225), based on integrated `main=4b1d219c2ba1739dc20c9c103170beedff8c1607` (PRs #224 and #226). **Not merged, activated or physically tested.** No bearer token, usable activation link or droplet change has been issued. Runner CI, exact-SHA review and the protected/physical gates remain mandatory.

## Decision and browser contract

The owner requested one private URL with a one-use key that opens directly in Chrome on the tablet, through the existing Termius SSH forward. No terminal, certificate authority, generated TLS certificate, public web host or shared reverse proxy may be required. The only origin is `http://localhost:8443`, with WebAuthn RP `localhost`; the only eventual droplet host publication is `127.0.0.1:8443:8443/tcp`. All other apps, ports, shared Docker installations, proxies, firewalls and web-server configurations are strictly out of scope. If the port is occupied, stop; never remove the occupant.

The proposed private activation URL is **a template, not a usable link**: `http://localhost:8443/activar#key=<43-character-base64url-secret>`. The key is 32 cryptographically random bytes generated outside GitHub; the protected host workflow must receive *only* SHA-256 of those raw bytes (hex64), never the bearer secret or a usable URL. The key is in the URL fragment, not a query: no HTTP GET transmits it. The dedicated same-origin JavaScript calls `history.replaceState` before asynchronous work and sends the raw key only once in a private JSON POST to `/begin`. Removal of the displayed fragment requires JavaScript to load; it is not a guarantee about browser history or backups. Scripts, external resources and storage are limited by CSP and the UI; no client key is placed in cookies, local storage or GitHub. The server validates the canonical token and its digest using constant-time comparison and burns the grant on first attempt. The browser cannot log in by presenting a public SHA-256 digest.

The UI requires one accessible activation button and the **native device-verification prompts** needed to create and prove a passkey. `navigator.credentials.create` requests a platform ES256, discoverable credential with user verification required. A separate `navigator.credentials.get` validates possession, UV, exact RP hash and origin. This is a 15-minute bounded service with individual 120-second WebAuthn operations; any invalid POST, expired state, replay or failed proof closes the one-use session. Browser storage/synchronization and actual Termius forwarding on Samsung/Chrome remain physical acceptance gates. A single Chrome visit cannot prove persistence across reinstall or on iOS.

## Critical custody isolation

The **HTTP-facing container may NEVER mount** `boca-socios_boca_owner`, `boca-socios_boca_key`, `boca-socios_boca_data`, the host web root or a host Docker socket. The Boca owner volume contains a private X25519 recipient key; it is reserved for offline operations. The temporary server takes only a public, fingerprint-checked recipient receipt, owner ID and 256-bit capability **digest**. After WebAuthn create→get succeeds, it calls the existing purpose-separated `seal_for_recipient` for `boca-owner-passkey-v2`, containing only credential ID and ES256 SPKI DER. It writes one bounded **ciphertext** file, `owner-envelope.v2` mode 0400 with exclusive create/fsync, into the separate labelled Docker **named volume** `boca-socios_owner_enroll_staging` (never a host bind mount). It does not output ciphertext to the browser or logs; it cannot read the recipient private key or install the owner credential. If an envelope is already staged, initialization fails closed; no partial success is reported as an installed owner.

After the HTTP server and its container are positively stopped, the protected host implementation invokes `owner_bootstrap.install-staged` in a different `--network none` container mounting the validated owner volume RW and the same staging named volume **read-only**, followed by `owner_bootstrap.verify` with owner read-only. The HTTP process never sees the owner key; the importer has no network; the ciphertext is not copied into Actions, Docker arguments, host stdout or a bind path. Only then is an owner credential CONFIGURED. No plaintext credential or capability may be passed as a GitHub input, Actions log or artifact. The temporary envelope, container, network and staging must be selectively removed immediately after success **or failure**, without Docker-wide prune or effect on any foreign resource. Persisted owner/key/data volumes are preserved, including on uncertain failures. A runner/SSH/docker interruption is NO-GO and requires a new read-only inventory before any retry.

## Protected workflow candidate and distinct activation gate

Issue #225 adds `owner-enroll` to the **existing** protected `boca-first-deploy.yml` manual workflow; no second deployment workflow is created. Its job requires current `main`, a reviewed image digest and protected environment/SSH gates, accepts only SHA-256 of the private URL key, then streams the pinned helpers over SSH. Before side effects, it checks the prepared owner volume and the dedicated rootless daemon, refuses an occupied `127.0.0.1:8443` without touching its listener, and writes a bounded provenance marker. It creates only one temporary labelled Boca bridge network **without IP masquerading/intercontainer communication**, the named staging volume and a container publishing **exactly** `127.0.0.1:8443:8443/tcp`. This bridge needs a gateway for Docker's host-loopback publication; an `--internal` bridge does not work for the listener (observed in [runner 41348070428](https://github.com/mbalbo2023/boca-socios-assistant/actions/runs/41348070428)). Disabled masquerading limits outside connectivity but is **not an absolute no-egress guarantee**; the HTTP service itself makes no external requests. No TLS, certificate, Termux, reverse proxy, other host port, shared Docker or unrelated app is changed.

The service has a maximum 900-second lifetime. The protected job waits for a successful Chrome create→get proof, verifies the stopped container, performs offline import/verification, then **always** runs the dedicated `host_cleanup.py --enroll` after an attempted enrollment stage. Cleanup validates the exact container, network, named volume, marker and any new unshared image before removing only those disposable objects. It preserves `boca-socios_boca_owner`, key/data volumes, pre-existing images and foreign Docker resources. No `docker prune` or global cleanup is allowed. A partial cleanup failure is `INDETERMINADO` and bars blind retries. The existing `beta-install` cleanup in ADR0090 remains mandatory and separate.

Unit tests and a disposable-runner HTTP/network/offline-import smoke are in this PR candidate. **Only successful hosted checks, review and merge can establish that code is integrated**, not that a real URL is usable. A fresh matching release, safe host preflight, private link delivery, real Chrome/Android passkey, Termius forwarding, post-restart access and BETA install/acceptance are distinct gates; no host execution is authorized by the PR alone.

The owner recipient is read in an offline container with the owner volume **read-only**: `inspect-prepared` never creates a private key and requires an earlier protected `owner-prepare`. After the Chrome proof is staged, Actions checks current `main` once more **before** running the offline private-key importer; a stale commit stops and triggers selective cleanup.

Never describe a successful synthetic proof or a staged ciphertext as a working Chrome link or deployed BETA. First-owner completion requires an exact-main release, protected host and SSH checks, a verified private URL, a real Android passkey, offline custody verification, then a separate BETA installation and acceptance. No actions on unrelated applications are authorized.

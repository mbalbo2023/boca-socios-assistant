# ADR 0092: Single-use Chrome owner enrollment without opening the owner volume to HTTP

**Status:** code candidate for [issue #225](https://github.com/mbalbo2023/boca-socios-assistant/issues/225), based on integrated `main=93c14ee5d939fd7d6abf56a57843c23c32b281c3` (PR #224). **Not host-integrated or physically tested.** No token or functional activation link has been issued; no change has been made to the droplet.

## Decision and browser contract

The owner requested one private URL with a one-use key that opens directly in Chrome on the tablet, through the existing Termius SSH forward. No terminal, certificate authority, generated TLS certificate, public web host or shared reverse proxy may be required. The only origin is `http://localhost:8443`, with WebAuthn RP `localhost`; the only eventual droplet host publication is `127.0.0.1:8443:8443/tcp`. All other apps, ports, shared Docker installations, proxies, firewalls and web-server configurations are strictly out of scope. If the port is occupied, stop; never remove the occupant.

The proposed private activation URL is **a template, not a usable link**: `http://localhost:8443/activar#key=<43-character-base64url-secret>`. The key is 32 cryptographically random bytes generated outside GitHub; the protected host workflow must receive *only* SHA-256 of those raw bytes (hex64), never the bearer secret or a usable URL. The key is in the URL fragment, not a query: no HTTP GET transmits it. The dedicated same-origin JavaScript calls `history.replaceState` before asynchronous work and sends the raw key only once in a private JSON POST to `/begin`. Removal of the displayed fragment requires JavaScript to load; it is not a guarantee about browser history or backups. Scripts, external resources and storage are limited by CSP and the UI; no client key is placed in cookies, local storage or GitHub. The server validates the canonical token and its digest using constant-time comparison and burns the grant on first attempt. The browser cannot log in by presenting a public SHA-256 digest.

The UI requires one accessible activation button and the **native device-verification prompts** needed to create and prove a passkey. `navigator.credentials.create` requests a platform ES256, discoverable credential with user verification required. A separate `navigator.credentials.get` validates possession, UV, exact RP hash and origin. This is a 15-minute bounded service with individual 120-second WebAuthn operations; any invalid POST, expired state, replay or failed proof closes the one-use session. Browser storage/synchronization and actual Termius forwarding on Samsung/Chrome remain physical acceptance gates. A single Chrome visit cannot prove persistence across reinstall or on iOS.

## Critical custody isolation

The **HTTP-facing container may NEVER mount** `boca-socios_boca_owner`, `boca-socios_boca_key`, `boca-socios_boca_data`, the host web root or a host Docker socket. The Boca owner volume contains a private X25519 recipient key; it is reserved for offline operations. The temporary server takes only a public, fingerprint-checked recipient receipt, owner ID and 256-bit capability **digest**. After WebAuthn create→get succeeds, it calls the existing purpose-separated `seal_for_recipient` for `boca-owner-passkey-v2`, containing only credential ID and ES256 SPKI DER. It writes one bounded **ciphertext** file, `owner-envelope.v2` mode 0400 with exclusive create/fsync, into a distinct private disposable staging directory. It does not output ciphertext to the browser or logs; it cannot read the recipient private key or install the owner credential. If an envelope is already staged, initialization fails closed; no partial success is reported as an installed owner.

After the HTTP server and its container are positively stopped, the **future protected host operation** must transfer that ciphertext only through a trusted private local channel and invoke the existing `owner_bootstrap.install` inside a different `--network none` container mounting the validated owner volume RW, followed by `owner_bootstrap.verify` RO. Only then is an owner credential CONFIGURED. No plaintext credential or capability may be passed as a GitHub input, Actions log or artifact. The temporary envelope, container, network and staging must be selectively removed immediately after success **or failure**, without Docker-wide prune or effect on any foreign resource. Persisted owner/key/data volumes are preserved, including on uncertain failures. A runner/SSH/docker interruption is NO-GO and requires a new read-only inventory before any retry.

## Implementation and host gate are separate

This first candidate provides an isolated WSGI service, browser UI, exact origin and one-use authorization, synthetic WebAuthn proofs, v2 ciphertext staging and unit tests. It intentionally does **not** modify the protected deploy workflow, rootless Docker host helper, Compose port binding or live droplet. The second cut must explicitly implement bounded manual Actions orchestration, positive container/volume provenance, same-job cleanup, stop-on-BUSY port, secure private link delivery and the no-network install/verify handoff, with disposable runner tests and separate owner approval for the host execution. The existing `beta-install` failed-attempt cleanup from ADR0090 remains mandatory and independent.

Never describe a successful synthetic proof or a staged ciphertext as a working Chrome link or deployed BETA. First-owner completion requires an exact-main release, protected host and SSH checks, a verified private URL, a real Android passkey, offline custody verification, then a separate BETA installation and acceptance. No actions on unrelated applications are authorized.

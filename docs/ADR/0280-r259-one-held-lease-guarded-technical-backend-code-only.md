# ADR 0280 — R259: actor técnico con una lease y recibos reales (CODE_ONLY)

**Fecha:** 13-NOV-2026 UTC / 12-NOV ART. **Issue:** #417. **Estado:** código candidato, `DEPLOY NO_GO`.

## RCA

R253 conserva un ensamblado de una sola `SuccessorPairJournal`, pero el tipo concreto `PostflightGatedSuccessorBackend` lleva `requires_persistent_receipt=False` y `successor_postflight_gate=None`: un `ACCEPT` textual de cleanup no puede promover ese actor. R257 introdujo una terminal técnica duradera sin passkey; R255 separó huellas pre-PARK de CIDs nuevos post-cleanup. No existía un actor que obligara a recorrer ambos tramos bajo **la misma** `BocaJobLease` del motor R256.

La secuencia del motor sigue `commit_marker → retire_old → finalize → terminal`. El par viejo puede ser borrado después del commit irreversible y antes del terminal. No se promete un rollback ni se pretende conservar cuatro CIDs en una topología cuyo cleanup SUCCESS exige exactamente dos nuevos. Esta decisión exige evidencia previa fuerte, una ejecución protegida, y fix-forward en cualquier indeterminación posterior al marcador; **no autoriza repetir R186**.

## Decisión y garantías de código

`GuardedTechnicalSuccessorBackend` es un wrapper de tipo exacto, no una copia del instalador histórico. Exige al construirse el grafo R253, la terminal R257 que lo referencia por identidad y una lease Boca validada. Cada operación verifica plan, lease y journal durable; no crea una lease ni usa Docker hasta que el único motor la invoque desde un contexto realmente protegido.

1. `attest` usa el actor reutilizable y captura `PreParkExpectedSeed` R255 con doble observación del par viejo, volúmenes, SQLite estructural y estado `SITE_URL` **antes de STAGE/PARK**. Un seed inválido, CID anterior no verificable o drift impide las operaciones effectful. `ATTESTED` guarda sólo hash real; `NOT_CONFIGURED` sólo expresa ausencia atestada, nunca un hash fabricado.
2. Todas las fases `stage`, `park`, creación de worker/controlador, aceptación fría, binding, retiro y compensación delegan al backend reutilizable existente, con los CIDs y límites Boca originales. El wrapper rechaza cualquier fase effectful sin seed genuino. No cambia Docker global, puerto, red ni composición ajena.
3. `finalize` se consume **antes** de cualquier efecto. Reutiliza explícitamente `ReusablePairUpgradeBackend.finalize` sobre el backend ya validado para ejecutar una sola vez el oficial SUCCESS cleanup V2, porque el viejo `PostflightGatedSuccessorBackend.finalize` tiene un gate de login/monitor `None` que no representa /healthz técnico. Sólo después del recibo `ACCEPT` real deriva el `PostflightExpected` de R255 desde CIDs/imágenes observados; coteja IDs del motor y llama a `ProductionBocaVolumeAttestor` + R257 O_EXCL técnico. Un fallo devuelve `INDETERMINATE` sin reintentar cleanup ni restaurar el par tras commit.
4. `requires_persistent_receipt=True` permite que el motor reconozca el tipo en una integración futura. El helper privado `_execute_reviewed_successor(preflight)` arma una única `backend_factory(plan, held_lease)` R256, el mismo `journal.intent/commit` y sink R257, con factory de un uso y validación de recibo canónico. **`main apply` NO llama al helper**; sigue rechazando antes de adquirir lease hasta completar todas las puertas físicas. No se declara BETA GO por schema2 técnico: passkey/Chrome, SITE_URL real, START/STOP, monitor/SQLite y aceptación owner requieren postflight físico independiente.

## Barreras restantes, decisión de promoción

- R259 `NOT_CONFIGURED` se acepta sólo por perfil schema2 *technical-cold-worker* con observaciones auténticas de ausencia tanto en controlador como en volumen de espejo; schema1/owner siempre lo rechaza. Este contrato fue implementado en ownership independiente, ADR0281, pero aún requiere el preflight físico y CI consolidado antes de habilitar APPLY. El wrapper veta `COMMIT_MARKER` si el nuevo candidato no supera la doble constatación precommit de SITE_URL bajo la misma lease.
- La captura estructural R255 por UID host 10001 puede NO_GO bajo remapeo `subuid` rootless: observar y validar mapa UID/GID e inodos reales en Action exclusivamente READ_ONLY antes de abrir APPLY. El panel previo sólo demuestra SQLite `VERIFIED_STABLE`, no custodia remapeada.
- Nueva fuente Python requiere allowlist idéntica builder/memfd y tamaño ZIP exacto bajo los límites vigentes del contrato R258, con reserva positiva y comprobación de import `-I -B`. El par histórico R253 tenía 2.978 B de margen; el owner del bundle R259 amplió el límite descomprimido a 1.500.000 B sin relajar el ZIP comprimido de 480.000 B, añadió cierre R255/R257/R259 y pruebas de import aislado. El tamaño y la reserva deben recalcularse sobre el SHA final, no darse por heredados.
- El CLI `main apply` futuro debe autenticar runners+release dual desde memfd y llamar al helper `_execute_reviewed_successor` **únicamente** después de validar el paquete, Action, preflight y revisión final. El helper ya une `backend_factory(plan, held_lease)` R256 *después del intent* y `OneShotTechnicalTerminalBridge` como único sink; no crea autoridad desde un objeto Python. Los interlocks operativos `main apply`/Action permanecen NO_GO en este corte.
- Todo efecto requiere main SHA exacto, PR0, CI/security Green, dos manifiestos/digests nuevos, censo Boca-only fresco, un único Actions protegido, CLEANUP V2 SUCCESS genuino, terminal y postflight owner físico. No borrar datos ni imágenes inciertas; PPI/Porota y servicios externos intocables.

# ADR 0091: SSH-only localhost HTTP; no device certificates

**Status:** candidate implementation in issue #223, based on `main=8a7bcf433a83071cc5ccee327c35743d349ce930`. The exact candidate PR, technical review, CI and merged HEAD must be recorded after review. There has been **no droplet operation, physical tablet enrollment or Boca BETA installation** under this decision.

## Owner decision and scope

The owner rejected the Android certificate/CA/Termux path and chose the existing Termius SSH connection. The target is **exactly** `http://localhost:8443` with WebAuthn RP ID `localhost` in Chrome on the tablet. Termius must forward tablet `127.0.0.1:8443` to droplet `127.0.0.1:8443` over its pre-existing authenticated SSH connection. This replaces ADR0088's HTTPS localhost and ADR0089's *device-local* certificate emitter as the proposed first-owner route; those ADRs remain historical records, and the old code is not a procedure to give the owner. Chromium and the WebAuthn specification permit the exceptional potentially trustworthy `http://localhost` context (see [Chromium WebAuthn origins](https://chromium.googlesource.com/chromium/src/+/main/content/browser/webauth/origins.md) and [W3C WebAuthn](https://www.w3.org/TR/webauthn-3/)). HTTP on DNS, IP addresses, alternate `.localhost` names, another port, or a noncanonical Host/Origin remains denied. The existing HTTPS DNS library path is retained for historical tests, but BETA Compose is restricted to the single reviewed HTTP localhost origin.

No host web-server, Nginx, Apache, Caddy, shared proxy, firewall rule, DNS, certificate, existing app or other port is changed. The Boca-only Compose container listens internally on its bridge but **Docker publishes solely `127.0.0.1:8443:8443/tcp`** on the droplet. A protected Boca-only port check must show that exact host port available immediately before install; BUSY/ERROR means STOP, with no attempt to stop or reconfigure whoever uses it. The only host operator remains the protected Boca Actions workflow, with current main/digest, owner, UID/cgroups, volume isolation and capacity gates. The staged-install failure cleanup from ADR0090 remains mandatory, immediate and selective, preserving owner/key/data volumes and every foreign resource.

For this SSH-only origin, owner custody encrypts **only** the public WebAuthn credential ID and ES256 public key in a new purpose-separated `boca-owner-passkey-v2` envelope. The recipient private key stays protected in the dedicated Boca owner volume; the actual passkey private key stays with the device credential manager. A v1 TLS envelope cannot be replayed as a v2 credential. The image-side preflight rejects TLS paths and residual certificate/CA entries for this mode; the runtime, health probe and synthetic acceptance use local plain HTTP and report `local_http=verified`, never falsely reporting TLS. The private browser UI checks exact scheme, Host, Origin, RP hash, user verification, CSRF and single-owner sessions. Its session cookie keeps `HttpOnly`, `Secure`, `SameSite=Strict` and the `__Host-` prefix; **real Chrome Android cookie acceptance must be tested** under the localhost exception. Safari's localhost Secure-cookie behavior is unverified and may differ. A browser cookie does not store the passkey permanently.

## Security tradeoff and remaining bootstrap gate

SSH encrypts and authenticates the tablet-to-droplet transport, but localhost HTTP **does not authenticate the locally listening process** or protect against a hostile local Android application that races to occupy the forwarded port. This is an explicit restriction to a privately administered tablet; no assertion of equivalent general HTTPS security, and no public HTTP access. The server must not trust forwarded-proto or identity headers. The Chrome passkey is origin-bound; the exact HTTP `clientDataJSON.origin` must match the enrolled coordinate, and the server rejects replays and other origins. Each authorized device needs its own active SSH forward.

The owner's requested **single-use Chrome registration URL containing a key is not yet implemented**, and no link can be issued from code or an uninstalled host. A separate, reviewed host-served first-owner enrollment phase is required on the *same* Boca-only port before the final panel starts. It must issue an independently authorized 256-bit one-use capability with a short deadline, consume it atomically, perform WebAuthn create→get with required user verification and discoverable credential, then persist only the public key and immediately close its listener. Its capability **must not enter public GitHub Actions logs, issues, PRs, workflow input history or screenshots**; a private handoff channel must be established and checked before any host activation. Only after the capability design, real Chrome/GPM behavior, stable Termius forwarding and owner custody are physically verified may #209 and #223 allow BETA deployment. This candidate does not silently wire anonymous passkey registration into the running panel.
